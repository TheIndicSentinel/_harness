# Measuring whether the harness helps

The harness records cost and a re-exploration signal automatically. Whether it helps needs a fixed task set, run the same way before and after a change. With one user and small samples this shows **direction, not statistical significance**; treat it that way.

## What is recorded for you
| Signal | Where | Reading it |
|---|---|---|
| Active time, est. tokens, branch | cost log (`~/.claude/harness/cost/<project>.md`) | sessions per branch is a task proxy |
| **Orient** (Read/Grep/Glob calls plus shell reads: `cat`, `sed`, `head`, `rg`, `grep`, `ls`, `find`; before the first edit) | same log | **a trend signal, not a score.** Comparable only within one project and one task type. A refactor reads more than a one-line fix |
| Memory health | `scripts/memory_lint.py` | hygiene (no status logs, verified dates), not usefulness |
| Live settings drift | `/harness-status` | whether the template and your live file agree |

## The baseline protocol (you run this; the harness can't)
1. Per project, pick **5 representative tasks** and write each as a fixed prompt: a bugfix, a small feature, a resume-after-3-days, a refactor, a "why does X work this way". Keep the prompt text identical before and after.
2. Run them **before** the change under test (a new CLAUDE.md, memory pruning, a handoff, a rule) in fresh sessions, one task per session, from a clean tree.
   **Worktrees and memory (checked 2026-10-16):** a git worktree does not get its own auto-memory. Claude Code keys memory to the main repository, so a worktree session loads the project's live memory directory whatever you copy into a folder named after the worktree. To control memory for a run, pass `--settings '{"autoMemoryDirectory": "<frozen copy>"}'` (verified with `claude -p /context`, which costs nothing), or set `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` for a no-memory variant. Only `MEMORY.md` is loaded into context; the other memory files reach the model only if it reads them.
3. Record per task, in a table you keep outside the repo:

| Task | Minutes to first correct edit | Orient (from cost log) | User corrections of things already in memory/CLAUDE.md | Test output shown? (y/n) | Tokens |
|---|---|---|---|---|---|

4. Make the one change. Re-run the **same** tasks in fresh sessions on a comparable starting commit.
5. Compare medians per column. One change at a time; otherwise you can't attribute the difference.

## Caveats
- The model, the prompt and the day's load vary; repeat each task twice if a result will drive a decision.
- Don't optimise Orient to zero. A session that reads nothing before editing may simply be editing blind.
- "Corrections" is the most informative column and the only one that needs your judgement; count a correction only when the information was already written down.
- **Orient definition changed on 2026-10-16.** It originally counted only Read/Grep/Glob and undercounted badly, because models explore through `Bash`. It now includes shell reads. When comparing a "before" taken under the old definition with an "after" under the new one, recompute both from the transcripts (`orientation_calls(path, include_shell_reads=False)` gives the old number).

## Where the atlas gets baseline numbers
The atlas panel "Harness cost vs measured benefit" reads `~/.claude/harness/baseline/<project>-compare.json` (schema 1): `cells[variant][task]` with `wall_s`, `in_out`, `cache_read`, `cost_usd`, `turns`, `orient_old`, `orient_new` (null for tasks that make no edit), plus `runs_per_cell`, `commit` and `notes` (confounds). Variants are `before`, `control` and `after`. A file entered by hand from pilot runs has no script in the repo that writes it, so the panel labels it **"Source: hand-entered from the pilot"** and marks each metric as `cross-checked` or `hand-entered only`. Optional fields drive that: `provenance` (free text shown on the panel), `cross_checked` (metric keys that match machine-written cost rows) and `generated_by` (set only by a script that regenerates the file; the label then reads "generated by <script>"). Only the metrics listed in `cross_checked` are compared with the hook-written cost rows; wall time, cache-read tokens, cost and turns are normally not cross-checked.

The noise rule is stated on the panel and in `scripts/cost_benefit.py`: the control's drift from `before` is the noise floor (at least 10%), and a result that one task accounts for 60% or more of is marked as such.

Glossary — 12 terms, for a reviewer with no prior harness context
Gate
A named check (e.g. privacy_guardrails_review) that must show a current pass before release_gate.py allows a recognized ship command through.
Required vs. advisory gate
Required gates are listed in gates.json's required_gates and mechanically block a ship. privacy_guardrails_review is always required; qa_review/compliance_review are opt-in per project.
Stale
A gate recorded "pass" for a commit that is no longer HEAD — new commits landed since the review, so the pass no longer covers the current code.
Dirty tree
Uncommitted local changes on top of HEAD. Since c2d0b3a, this blocks a ship even if the recorded gate is a current pass — a passing gate only vouches for committed content.
Self-attestation
Nothing but honesty stops a gate record from being hand-written as "pass." Required-status-checks in branch protection raise the ceiling; they don't remove this limit.
Project memory
Claude Code's own native per-project store (~/.claude/projects/<path>/memory/), not a harness invention — some skills write durable decisions there.
CI wiring (vs. present)
The harness-gate-check.yml template existing in a repo protects nothing until another workflow actually calls it via `uses:` — presence alone is inert.
Budget skipped
An explicit `--skip` recorded for a project's token budget — reads as a deliberate choice in project health, not a silent gap.
Project health
An informational 0–6 score (CI wired, release command documented, etc.) — not a gate. A real prototype can score low and still be fine.
Meta project
_harness itself — excluded from gate/docs/session tracking by design (project_root_for() skips any path starting with "_harness").
Evidence
A concrete artifact proving a claim: a commit SHA, a gates.json entry, a memory file, a COST_LOG.md row — not a description of intent.
Trust level
Local record (self-attested, this machine only), CI-verified (a GitHub Actions check ran against it), or manual (a human confirmed it outside any tooling).
